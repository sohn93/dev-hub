문제 제약 설계 판단 구현 경계 검증 남은 한계
01 · PROBLEM

새 게임마다 전체 프로젝트를 복사하면,
공통 기반과 게임 규칙이 함께 따라왔습니다.

Kitty Guardians 프로젝트에는 재사용할 가치가 있는 모바일 공통 기능과, 특정 게임에서만 의미가 있는 콘텐츠·경제·보상 정책이 섞여 있었습니다.

그 상태에서 복사 후 삭제하는 방식은 빠르게 시작할 수 있지만, 무엇을 지워도 되는지 매번 다시 판단해야 합니다. Firebase Auth, Google Sign-In, PlayFab, IAP처럼 다음 프로젝트에 필요하지 않은 연동도 함께 따라오고, 게임 코드가 SDK 타입을 직접 알수록 분리는 더 어려워집니다.

목표

장르가 달라도 남는 Android 모바일 게임 기반만 보존하고, 새 게임의 정책과 콘텐츠가 들어갈 자리를 명확히 비워두는 것.

02 · CONSTRAINTS

코드를 옮기는 것보다
경계를 증명하는 일이 중요했습니다.

  • UI는 UI Toolkit이 아니라 기존 제작 흐름과 맞는 uGUI와 TextMesh Pro를 사용합니다.
  • Firebase는 App, Analytics, Crashlytics만 남기고 Auth는 제외합니다.
  • 광고는 Google Mobile Ads와 UMP 동의 흐름까지만 공통 기반으로 봅니다.
  • 씬과 프리팹 연결은 런타임 탐색 없이 serialized reference로 명시합니다.
  • SDK 설정이 없더라도 샘플 앱의 기본 흐름은 시작할 수 있어야 합니다.
  • 릴리스 구성 오류는 실행 중이 아니라 빌드 전에 차단해야 합니다.
03 · DECISIONS

공통 기능은 Core로,
외부 변화는 adapter로 밀어냈습니다.

CoreuGUI · lifecycle · contracts
FirebaseAnalytics · Crashlytics adapter
AdsGoogle Mobile Ads · UMP adapter

1. 게임 코드는 SDK 타입을 모릅니다

IAnalyticsService, ICrashReportingService, IAdService가 Core에 있고, 각 SDK 패키지가 계약을 구현합니다. Core 정적 검사에서 Firebase와 Google Mobile Ads 참조가 0건임을 확인했습니다.

2. SDK 부재는 복구 가능한 상태입니다

Null 구현과 서비스 초기화 결과를 통해 SDK 미설치·설정 누락·초기화 실패를 구분합니다. 선택적 서비스가 실패해도 초기 화면으로 이동하는 앱 흐름은 유지됩니다.

3. 빌드 목적마다 검증 기준이 다릅니다

깨끗한 템플릿, 개발 빌드, 릴리스 빌드가 요구하는 조건을 분리했습니다. 공식 샘플 광고 ID는 템플릿과 개발 단계에서는 허용하지만, 릴리스에서는 차단합니다.

완료의 기준을 파일 이동이 아니라
실제 빌드와 경계 검사로 잡았습니다.

06 · LIMITS

확인하지 못한 것은
성공으로 적지 않았습니다.

남은 검증

연결된 Android 기기가 없어 설치·실행 smoke test는 수행하지 못했습니다. 새 게임의 google-services.json도 의도적으로 없으므로 Analytics·Crashlytics live delivery는 확인 대상에서 제외했습니다.

또한 embedded package를 복사형 스타터로 사용하는 단계까지가 현재 범위입니다. 여러 게임에 중앙 배포하려면 이후 Git UPM 또는 private registry 운영 모델이 별도로 필요합니다.
